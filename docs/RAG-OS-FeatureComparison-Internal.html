RAG-OS vs Azure: strategy review

A candid comparison of RAG-OS with Microsoft Foundry IQ and Azure AI Search document-level access. Every claim here is checked against the code as it stands, and the document names the course corrections to make before the market forces them.

  • Audience Founder and architects
  • Evidence Code inventory, Microsoft Learn and market scan, all checked 9 Oct 2026
  • Companion RAG-OS-FeatureComparison.html (external edition)
  • Direction is rightPolicy-based access and governed classification are real gaps that Azure's native features don't cover.
  • Claims need trimmingThe Overview overstates "no per-token cost" embeddings (live dev runs Azure OpenAI 3-small) and leaves out admin tracing entirely.
  • Microsoft is closing inFoundry IQ went GA in June 2026, and native ACL and Purview ingestion are in preview, all in the same Azure AI Search we run on.
  • Adopt, don't rebuildTake SharePoint ACLs, OCR, Purview label metadata and quotas from Azure. Keep policy, classification, grounding and tracing custom.

Contents

    1Verdict on one page

    RAG-OS is pointed at a real gap, but it is a narrower product today than the Overview implies. The platform underneath it (Azure AI Search) is moving toward governed RAG quickly. The plan should be to sit on top of Microsoft's stack, not compete with it.

    • The direction is broadly right. Policy-based access is the differentiator: department any-of, hierarchical region, clearance level and personal share, combined with default deny and compiled into a pre-filter that runs inside the search. Azure's native document-level access understands only userIds, groupIds, rbacScope and Purview labels. A match on any of them grants access, and there is no hierarchy or clearance logic. Microsoft's own guidance is to use security filters (the RAG-OS pattern) for custom policies. Layered classification with SME review and per-facet provenance has no counterpart in the Foundry IQ docs we reviewed. That is absence in the docs, not a Microsoft statement.
    • The product is narrower than it reads. The working connectors are local folder, Blob and upload; SharePoint, Drive and FTP are stubs that raise NotSupported. There is no OCR, only one retriever (direct), and only single-tenant Entra. Customer-portal context injection doesn't exist yet. The live dev deployment embeds with Azure OpenAI text-embedding-3-small, not the self-hosted TEI model the Overview leads with.
    • Risk 1: Microsoft builds governed RAG into the same Azure AI Search. Foundry IQ went GA on 2 June 2026 (narrow scope). Native SharePoint and ADLS ACL ingestion, Purview labels and a per-knowledge-base MCP endpoint are all shipping (the ACL and Purview pieces in preview). Every quarter, the "AI Search plus a UI" part of RAG-OS gets cheaper for anyone to copy.
    • Risk 2: seat prices have collapsed to about $20. Copilot Business is $21, Gemini Business $21, Quick Plus $20, Onyx $20 (with a free open-source edition), and Rovo comes bundled. An SMB knowledge-base SaaS sold per seat can't win on features alone.
    • Risk 3: the planned use cases are crowded. Questionnaires have Vanta, Loopio and Responsive. Quizzes have Copilot in Microsoft Forms. Form filling has ONLYOFFICE and Nanonets. Cited finance grids have Hebbia.
    • Top five moves:
      1. Correct the Overview this month: TEI wording, admin tracing, "hosted on Foundry", external portal users.
      2. Ship SharePoint through Azure AI Search's native ACL ingestion as a source-ACL mode ANDed with RAG-OS policy, isolated behind an adapter. Don't build our own ACL sync.
      3. Move "governed retrieval as an MCP server" from Later to Next. The goal is to become the policy gateway for Copilot, Claude and Foundry agents rather than one more chat UI.
      4. Ship evaluation release gates with a faithfulness score, and OCR through Content Understanding. Both are entry tickets for regulated verticals.
      5. Lead with regulated-vertical completeness (mortgage loss-mitigation, then prior-auth and KYC) plus the governed enterprise knowledge base. Defer the personal edition, Drive/FTP and the marketplace, and drop "fun quizzes".

    Internal positioning in one line: RAG-OS is the policy, classification and accountability layer on top of Azure AI Search and Foundry IQ, for documents whose source ACLs are missing or can't be trusted. It doesn't replace them.

    4.2 How the ADLS Gen2 POSIX-like ACL model works in Azure AI Search

    This is the one native ACL path that fits customers whose file shares already sit in Data Lake Storage Gen2 with folder permissions. That is exactly the "file-share corpus" RAG-OS targets, so architects should understand it before we pick a SharePoint or ADLS design.

    1. Storage model. In a hierarchical-namespace account, each directory and file carries POSIX-like ACL entries that grant read, write or execute to named users and groups. Access ACLs apply to the item. Default ACLs are copied to new children only; existing children don't inherit new defaults. Azure RBAC is evaluated before ACLs, so an ACL can't take away access a role already grants.
    2. Ingestion. An ADLS Gen2 indexer (from 2025-05-01-preview) or a Blob knowledge source with isADLSGen2 (from 2025-11-01-preview) sets indexerPermissionOptions / ingestionPermissionOptions. It walks container root → each directory → file, computes the effective access list per file, and writes it to the userIds and groupIds fields (metadata_user_ids, metadata_group_ids). Container-level RBAC (Storage Blob Data Reader) goes into rbacScope. When chunking, the ACL fields must be carried to each chunk with index projections.
    3. Query. The app sends its own credential in Authorization and the user's Entra token (scope https://search.azure.com/.default) in x-ms-query-source-authorization. The token's oid is matched against userIds, and groups are resolved live through Microsoft Graph, including nested groups. A match on any type grants access. The internal filter is appended to the caller's $filter.
    4. Required setup. Assign every group and user at root / with Read+Execute, also as Default, then "apply ACLs recursively" and remove excess entries.

    Limits that matter for RAG-OS:

    • Named users and groups only. The owning user, owning group and "Other" entries aren't supported in preview, and ADLS ABAC conditions aren't evaluated.
    • ≤32 ACL entries per file or directory (effectively 28). Entries beyond the limit "might not be enforced". In practice this pushes customers toward group-based ACL designs.
    • No live sync. ACLs are captured on the first crawl and for new files only. Later permission changes need a file touch, /resetdocs or /resync (preview). Otherwise the index keeps serving stale ACLs. Group membership changes do apply live.
    • Pipeline restrictions. Not supported with the Custom Web API skill, enrichment cache, knowledge store or asset store (so no image serving), debug sessions or the Azure portal. Fails closed (5xx) if Graph is unavailable.
    • Preview, with no SLA (latest 2026-08-01-preview).

    Sample caveat: the recommended cloud-ingestion flow in azure-search-openai-demo uses a custom Azure Function that parses each file's ACL string and "does not consider directory-level ACL inheritance". The reference demo cuts the same corner we would be tempted to.

    9Purview sensitivity labels: needed or complication?

    The question: where and how should Microsoft Purview Information Protection sensitivity labels be used alongside the attribute-based filter, and is this worth the complexity?

    Verdict: needed, but only as a classification input that feeds the existing ABAC filter. It must not become a second enforcement engine. One enforcement point stays: the OData pre-filter inside Azure AI Search. A label becomes another way to set acl_clearance and f_confidentiality, with provenance purview:<label>, in the same way a path rule or manifest row does today. Ignoring labels fails procurement in Microsoft shops. Adopting Microsoft's native label enforcement now would add a parallel access model that can't see the content we parse ourselves.

    9.3 Implementation notes for option B

    • Parse both metadata locations. Office stores the label either as custom document properties (docProps/custom.xml, keys MSIP_Label_<GUID>_Enabled, _SetDate, _Method, _SiteId and so on) or in the LabelInfo part (in practice docMetadata/LabelInfo.xml). When a tenant enables co-authoring for labelled files, new labels go only to LabelInfo, existing files migrate on next save, and custom.xml isn't kept in sync. Reading only the custom properties reports those files as unlabelled, which is the failure mode Microsoft documents. Follow MS-OFFCRYPTO 2.6.3: prefer LabelInfo when it holds a label for the tenant's siteId, and honour removed="1". Only Word, Excel and PowerPoint are affected.
    • PDF labels are out of scope for v1. We haven't verified where the label sits inside a PDF. Until a spike confirms it, PDFs fall through to the other layers and the docs must not claim PDF label support.
    • SharePoint, when the connector lands: Graph v1.0 driveItem: extractSensitivityLabels (least privilege Files.Read.All, not metered). It returns 423 for double-key-encrypted files and some edge cases.
    • An explicit mapping table in config, never automatic. Key it on (tenantId, labelId). Use Graph v1.0 GET /security/dataSecurityAndGovernance/sensitivityLabels/{id} (SensitivityLabel.Read) to fetch names and priorities and to propose rows, which a compliance admin and an SME then approve. Microsoft says a higher priority number "usually" means higher sensitivity, which isn't a guarantee. Sublabels share their parent's priority for justification, and a parent with sublabels can't be applied directly. Unknown, deleted or other-tenant GUIDs get a configurable fail-closed default. When the label catalogue is refreshed, flag priority reorders for review rather than silently re-stamping.
    • Layer position: after the sidecar, before the manifest. The order becomes source defaults → path rules → sidecar → Purview label → manifest → upload form → classifiers. SME review still overrides everything, with provenance. Proposed guard: a label-derived acl_clearance is a floor that later automatic layers can raise but only an SME review can lower.
    • No MIP SDK needed for unencrypted files. There is no Python binding (the SDK ships for C++, .NET and Java in preview), and labels are stored in clear text in file metadata, so a Python parse of the metadata is enough. A label change alters the file but not the extracted text, so it should take the existing RETAG path (merge, no re-embed). Confirm this in the spike.

    9.4 Encrypted (rights-protected) files

    Generic parsers can't read the content of a rights-protected file. The label is still readable: in an encrypted Office file the LabelInfo copy sits in the encrypted container's \x06DataSpaces storage and the legacy label in Doc SummaryInfo. (Our ability to read it reliably with an OLE library is untested.) The default should therefore be: skip the content, record the label, and show a protected_content status in the admin console, so the gap is visible rather than silent.

    Indexing the content would need an opt-in .NET or C++ MIP SDK sidecar running with Azure RMS super-user or Content.SuperUser rights. That identity can read all encrypted content in the tenant, so it needs the customer's formal governance approval, and it can't open double-key-encrypted content at all. Distributing a product built on the MIP SDK outside our own organisation needs an Information Protection Integration Agreement (IPIA) with Microsoft. Treat the sidecar as a paid, per-customer option, not a default.

    9.5 Complications to avoid

    • Labels as a parallel access model. A second "can this user see this label?" check next to ABAC means two engines to explain, test and keep in sync. Labels set attributes; ABAC decides.
    • Re-implementing Purview policy logic. We don't evaluate usage rights, DLP rules or label policies ourselves. If a customer needs that, option C (after GA) or their own Purview DLP is the place.
    • Making native enforcement mandatory. It's Preview, indexer-only, same-tenant and admin-heavy. Requiring it would block every deployment that uses our push pipeline or portal users.
    • Deriving clearance from priority numbers without a reviewed table. Priority is an admin ordering, not a sensitivity scale, and label reorders would silently change who sees what.

    13Appendix: further analyses, decision log and glossary

    TCO and pricing model

    Monthly Azure cost per deployment size (Container Apps, Search tier, PostgreSQL, Service Bus, GPU pool vs Azure OpenAI embeddings), set against Foundry IQ (50M free agentic tokens, Azure OpenAI billed separately) and $20–30 seat alternatives. Needs the per-1M agentic rate, which is unpublished today.

    Threat model (STRIDE) for the access path

    Token → claims mapper → policy → OData → Search → LLM. Cover filter injection (allow-list), admin bypass abuse, fail-open in agent paths, stale ACLs, prompt injection in retrieved passages, and cross-tenant leakage once multi-tenant ships.

    Evaluation benchmark plan

    A golden set per use case (the UC1 prototype has 11 cases), access-leak tests (users who must get no_access), abstention-rate and faithfulness targets, and release-gate thresholds.

    Demo script vs Foundry IQ

    Same corpus, two users: (1) a clearance and region rule Foundry IQ can't express natively; (2) explain why access was denied; (3) the trace after an MCP call (Foundry IQ's MCP returns no activity); (4) the review queue and provenance; (5) honestly showing where Foundry IQ wins (M365 reach, agentic planning).

    Decision log (ADRs)

    • ADR: az CLI PS7 over Bicep
    • ADR: ABAC is the authority over native ACLs
    • ADR: default embedding profile (TEI vs Azure OpenAI)
    • ADR: preview-adoption policy (adapter, flag, contract test)
    • ADR: MCP tool contract and identity flow
    • ADR: Retriever port and the Foundry IQ fail-closed rule
    • ADR: SharePoint ingestion option (merge vs push)
    • ADR: Purview labels are a classification input, not a second enforcement point

    ICP and positioning statement (draft)

    "For regulated organisations on Azure whose documents carry rules that file permissions can't express (department, region, clearance), RAG-OS is the governed knowledge layer that enforces those rules inside every search, proves every answer, and plugs into Copilot, Claude and Foundry agents. Unlike ACL-sync assistants, policy is the customer's, explainable and default-deny."

    Glossary

    ABAC / ACLAttribute-based access (rules over user and document attributes) vs access control lists (named principals per item).
    Security filterThe GA Azure AI Search pattern: a string-collection field plus a search.in filter supplied by the app on every query. RAG-OS extends it with ABAC.
    permissionFilterPreview index attribute marking userIds, groupIds or rbacScope fields for native trimming.
    x-ms-query-source-authorizationRequest header that carries the end user's Entra token, so Search can trim results natively.
    Knowledge base / sourceFoundry IQ objects: a knowledge base orchestrates agentic retrieval over up to 10 knowledge sources (indexed or remote).
    Elevated readPreview header that bypasses ACL trimming for debugging (Search POST only).
    Fail-open / fail-closedWhether a missing or failed security check returns everything (open) or nothing (closed).
    OBOOn-behalf-of token exchange, used to carry a user's identity through a service.
    MCPModel Context Protocol, the open standard for connecting agents to tools and data.
    Sensitivity labelA Microsoft Purview label that marks how sensitive an item is (and may apply encryption). RAG-OS reads it as an input to clearance (section 9).
    TEIHugging Face Text Embeddings Inference, the self-hosted embedding server.

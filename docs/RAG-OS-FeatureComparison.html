Competitive analysis · v1.0 · 9 October 2026

RAG-OS vs Azure Foundry IQ & AI Search

What Microsoft's platform building blocks provide, what RAG-OS adds on top of them, and how the two work together. The comparison is dated, because preview features change quickly.

  • Version 1.0
  • Date 9 October 2026
  • Audience Prospects and partners
  • Azure status checked 9 October 2026
  • Policy-based accessDepartment, region hierarchy, clearance and personal shares, enforced inside every search. Access is denied by default.
  • Governed classificationLayered tagging, an SME review queue and a record of where every tag came from.
  • Grounded answersPage-level citations, and an abstention when the permitted evidence doesn't support an answer.
  • Runs in your tenantYour Azure subscription, keyless managed identity, and models on Microsoft Foundry.

Contents

    1Executive summary

    Azure offers platform building blocks. RAG-OS is a governed knowledge product built on them. RAG-OS already runs on Azure AI Search and Microsoft Foundry models, and its roadmap adopts Foundry IQ underneath. The two work together; this is not an either/or choice.

    Microsoft Foundry IQ

    A managed knowledge layer over Azure AI Search agentic retrieval. A knowledge base wraps up to 10 knowledge sources (3 on the Free tier). GA was announced on 2 June 2026, and the first stable API is 2026-04-01. GA covers extractive retrieval at minimal effort over search-index, Blob, OneLake and Web sources. LLM query planning, answer synthesis, SharePoint, Work IQ and document-level permissions are still in Preview.

    AI Search document-level access

    Security filters (a string field matched with search.in) are Native GA. The native, Entra-token-enforced options are all Preview: ADLS Gen2 ACL and RBAC-scope ingestion, SharePoint ACL ingestion, Purview sensitivity labels, and query-time enforcement through x-ms-query-source-authorization.

    RAG-OS

    A knowledge assistant that runs in your Azure subscription. It adds an attribute-based access policy, SME-governed classification, answers that cite their sources or abstain, per-query token cost and tracing, and an embeddable chat. It uses the GA security-filter pattern Microsoft recommends for custom policy, and extends it.

    Key takeaways

    1. Different layers, not substitutes. Foundry IQ and AI Search retrieve content and trim results by identity. RAG-OS sits above them and decides who should see what, how documents are classified and when not to answer.
    2. Identity trimming versus policy. Azure's native access matches users, groups, RBAC scope, SharePoint groups and Purview labels, and a match on any one grants access. It has no hierarchy or clearance logic. RAG-OS compiles department, region hierarchy, clearance and personal-share rules into a filter applied inside every search, and denies access by default. Azure ANDs a caller's filter with its own permission filter, so the two can be combined.
    3. Classification is the open space. The Foundry IQ documentation we reviewed has no taxonomy authoring, document classification or human review queue. RAG-OS provides layered tagging, cost-capped auto-classification, an SME review queue and a source recorded for every tag.
    4. Azure is stronger in several areas, and this document says so. Those areas are agentic query planning and multi-source fan-out, first-party Microsoft 365 / SharePoint / OneLake reach, a native MCP endpoint for every knowledge base, a Microsoft-run service with no app to operate, a route to Purview labels and native ACLs, and the first 50M agentic tokens free each month.
    5. Maturity matters for governance. Document-level permissions in Foundry IQ are Preview only: they aren't in the stable 2026-04-01 API. Microsoft's documentation also describes cases where knowledge-base retrieval returns unfiltered results, for example when the user token is omitted. The APIs are changing fast. RAG-OS gives customers a stable product contract and can adopt these native features as they reach GA.
    6. The roadmap is built to work together with Azure. Planned work includes SharePoint through native ACL ingestion, Foundry IQ as an alternative retriever, Purview labels mapped to clearance levels, RAG-OS as an MCP server, and publishing as a Foundry agent for Teams and Copilot Studio.

    3Where each sits

    RAG-OS is a governance layer between the channels people use and the Azure retrieval and model services underneath. Azure AI Search is the retrieval engine today. Foundry IQ can be added underneath as an alternative retriever without changing the governance layer above it.

    • Today: RAG-OS compiles each user's access policy into a filter that Azure AI Search applies inside hybrid and semantic search, then sends only the permitted passages to a model on Microsoft Foundry.
    • With Foundry IQ (roadmap): a RAG-OS-built index can be wrapped as a search-index knowledge source, so agentic planning and multi-source fan-out sit under the same policy, classification and grounding layer.
    • With native ACLs (roadmap): for SharePoint, source permissions come from Azure's native ACL ingestion, and RAG-OS ANDs its attribute policy on top.

    5.1 Access control

    RAG-OS

    Attribute-based access policy

    What it is
    A declarative policy that matches user attributes from Microsoft Entra ID (department, region, clearance, employee ID) against access fields on each document. The rule is (department AND region AND clearance) OR personal share. A personal share is an exact employee ID, and wildcards never grant one. A role-gated "Only me" upload grants access to the uploader alone. New attributes, such as cost centre, are added in configuration, not code.
    Purpose
    Many document estates (file shares, uploads, exported archives) have no trustworthy source ACLs. A policy states the organisation's rules directly and applies them the same way across every source.
    Example
    A UK HR analyst with clearance 2 asks, "What is the parental-leave policy for contractors?" The search considers only HR or all-department documents tagged UK, EMEA or Global at level 2 or below. Documents in the Legal folder, and Restricted (level 3) HR files, are never retrieved.
    RAG-OSAvailableAzure equivalentBuild-it-yourself Native trimming is identity-based. Attribute rules are an OData filter you write and maintain.

    References: Security filters for trimming results · Document-level access overview · RAG-OS Overview §5

    RAG-OS

    Region hierarchy and clearance levels

    What it is
    Region values form a hierarchy (UK, then EMEA, then Global), so a UK user also sees EMEA-wide and global documents. Clearance is ordinal. A document's level must be at or below the user's clearance, and a document with no level is denied.
    Purpose
    This matches how organisations publish policy (global, regional, local) without tagging every document with every country. It also models confidentiality tiers that identity groups express poorly.
    Example
    A Paris-based finance manager (region FR, clearance 1) sees the global expense policy and the EMEA travel addendum. They don't see a UK-only bonus memo or a level 2 audit report.
    RAG-OSAvailableAzure equivalentBuild-it-yourself The native permission types are userIds, groupIds and rbacScope (plus Purview labels), and any match grants access. There is no hierarchy or level logic.

    References: Permission fields (push API) · Query-time ACL / RBAC enforcement

    RAG-OS

    Default deny and injection-safe filters

    What it is
    The policy compiles to an OData filter (search.in, le) that Azure AI Search applies on every search, facet and listing call. If a required attribute is missing, the result is deny-all and the search never runs. Each claim value is checked against an allow-list pattern first. A bad value is rejected (HTTP 401), never "sanitised". A property test checks that the compiled filter and the policy's reference logic always agree.
    Purpose
    Pre-filtering means restricted text never reaches the model, the logs or the answer. Default deny means a misconfiguration fails closed.
    Example
    A new joiner's Entra profile has no department yet, and they have no personal shares. Instead of seeing "whatever looks public", they get a no_access response until an admin sets the attribute.
    RAG-OSAvailableAzure equivalentPreview Direct search without a user token returns only public documents, and ACL evaluation failures return a 5xx error. Knowledge-base retrieval returns unfiltered results if the token is omitted or permission ingestion wasn't configured.

    References: Query-time enforcement · Knowledge base retrieve (permissions) · Connect Foundry IQ to an agent

    RAG-OS

    Explain access and audited admin bypass

    What it is
    An explain command prints the exact filter a given user's searches carry. Admins (Entra app role rag.admin) can bypass the filter to investigate, and every bypass is audit-logged. An admin-only "near-miss" probe explains a refusal by re-running the query without the access filter. Admins can also edit user attributes, which are written back to Entra through Microsoft Graph.
    Purpose
    Questions like "why can't she see the travel policy?" get an answer backed by evidence, without giving anyone standing broad access.
    Example
    A user reports "it says it has nothing on bonuses". The near-miss probe finds two documents at clearance 2, and the user is clearance 1. The system is working as designed, and support has a clear answer to give.
    RAG-OSAvailableAzure equivalentPreview The elevated-read header shows all documents on Search POST for manual comparison. It isn't available on knowledge-base retrieval, and there is no explain-why-denied API.

    References: Elevated read · Purview query-time audit

    Azure AI Search

    Security filters

    What it is
    A string-collection field on each document (for example, group IDs) and a search.in filter that the application adds to every query. The pattern isn't tied to an API version.
    Purpose
    Microsoft recommends it for custom identity systems, non-Microsoft security frameworks and push-model indexes. "The principal is just a string": the app resolves identity and must apply the filter on every query.
    Example
    An app stores group_ids per document and filters each request with group_ids/any(g: search.in(g, '…')) using the caller's group IDs.
    RAG-OSAvailable RAG-OS builds on this GA pattern and extends it with policy semantics.Azure statusNative GA

    Azure AI Search

    ADLS Gen2 POSIX-like ACL ingestion

    What it is
    The ADLS Gen2 indexer, or a Blob knowledge source on ADLS Gen2, reads the ACLs on the container root, each folder and the file. It computes the effective access list for each file and writes it into the userIds / groupIds permission fields. RBAC scope gives coarser, container-level access. See the walkthrough below the cards.
    Purpose
    It reuses permissions the data lake already holds, so you don't have to tag documents again.
    Example
    Files under /HR/Payroll/ are readable only by the Payroll-Admins group. After indexing, a query with an HR-Team member's token returns no payroll chunks. A Payroll-Admins member sees them.
    RAG-OSNot offered RAG-OS doesn't read ADLS ACLs. Because Azure ANDs a caller's filter with the native permission filter, the two can be combined.Azure statusPreview

    References: ADLS Gen2 ACL / RBAC indexing · Tutorial · ADLS access model · Pull-API quickstart

    Azure AI Search

    SharePoint ACL ingestion

    What it is
    The SharePoint indexer ingests each item's effective ACL and enforces it at query time. It covers inheritance from site to library or list to folder to item, unique permissions, Entra security and Microsoft 365 groups, and SharePoint site groups (from 2026-05-01-preview).
    Purpose
    Assistant answers stay in line with the SharePoint permissions people already manage.
    Example
    A project site shared with "Specific people" is visible only to those people. Items shared through "Anyone" or organisation-wide links aren't supported, and guests aren't covered.
    Limits
    Up to 1,000 entries per file. Item-level changes are picked up on each run, but inherited changes need /resync. An Entra group nested inside a SharePoint group isn't expanded. The indexer needs application permissions (Files.Read.All plus Sites.FullControl.All or Sites.Selected).
    RAG-OSRoadmap A SharePoint connector with permission sync, using Azure's native ACL ingestion.Azure statusPreview

    References: SharePoint ACL indexing · Remote SharePoint knowledge source

    Azure AI Search

    Purview sensitivity labels

    What it is
    Built-in indexers extract Purview labels from Blob, ADLS Gen2, SharePoint and OneLake. At query time the service evaluates the label, the user's token and the Purview policy (usage rights; the query-time documentation names EXTRACT). Results carry the label ID, and knowledge-base retrieval and MCP return label information for each reference.
    Purpose
    Microsoft customers already classify confidentiality in Purview, and honouring those labels avoids running a parallel scheme.
    Example
    A document labelled "Highly Confidential" is returned only to users whose Purview usage rights for that label allow it.
    Constraints
    Requires the search service's system-assigned identity. A Global Administrator or Privileged Role Administrator must grant Content.SuperUser and UnifiedPolicy.Tenant.Read. Single tenant only, with no guests. purviewEnabled can't be reversed, and the index then accepts RBAC only. No autocomplete or suggest. Content an app parses and pushes itself isn't covered, and labelled documents are skipped if the indexer uses the custom Web API skill, knowledge store, enrichment cache or debug sessions. Fails closed (5xx) if Purview can't be reached. GA is targeted for October 2026 on the Microsoft 365 roadmap.
    RAG-OSRoadmap Next phase: labels read at ingestion become a classification input, mapped to clearance and confidentiality under the same access policy. See section 6.Azure statusPreview

    References: Label indexing · Label enforcement at query time · Purview demo (GitHub)

    Azure AI Search

    Query-time token enforcement

    What it is
    The app sends the end user's Entra token (scope https://search.azure.com/.default, no Bearer prefix) in x-ms-query-source-authorization, alongside its own service credential. The service matches oid to userIds, resolves group membership through Microsoft Graph (nested groups included) and checks RBAC scope. It then appends this internal filter to any $filter the caller sends.
    Purpose
    Enforcement moves into the service, so the app can't forget the filter, and caller filters such as attribute rules can still be layered on top.
    Example
    A web app uses the on-behalf-of flow to forward a user's token. Documents whose groupIds include one of the user's (possibly nested) groups come back, and the app's own department filter narrows them further.
    Watch-outs
    The Foundry Agent Service's built-in Azure AI Search tool can't pass this header (open GitHub issue). The supported route is the knowledge-base MCP tool with a per-request header.
    RAG-OSAvailable RAG-OS has its own equivalent: it compiles and applies the policy filter on every call.Azure statusPreview

    How ADLS Gen2 POSIX-like ACLs become search permissions

    ADLS Gen2 uses POSIX-style access control lists on folders and files. To read a file, a principal must be able to traverse every folder on its path and read the file itself. The Azure AI Search indexer follows this hierarchical evaluation from the container root down to each file. It writes the final effective list of named users and groups into the index's permission fields. A simplified walk:

    / (container root)HR-Team, Finance-Team, Payroll-Admins can traverse
    →
    /HRHR-Team, Payroll-Admins
    →
    /HR/PayrollPayroll-Admins
    →
    salary-bands.pdfread: Payroll-Admins
    →
    groupIds = [Payroll-Admins]effective access written to the index

    6Purview sensitivity labels with RAG-OS access policy

    Purview sensitivity labels say how sensitive a document is. The RAG-OS access policy says who may see it. The two answer different questions, so they work best together.

    Microsoft Purview sensitivity labels

    A label such as General, Confidential or Highly Confidential is applied to a file by a person or an auto-labelling policy. It is stored in clear text in the file's metadata, so other applications can read it. A label can also encrypt the file and grant usage rights (for example view or extract) to named users and groups. Purview data loss prevention (DLP) policies use labels too, for example to stop Microsoft 365 Copilot processing labelled items.

    RAG-OS access policy

    A declarative policy that matches each user's attributes against each document's access fields: department, region hierarchy (UK, then EMEA, then Global), clearance level and personal share. It is compiled into a filter applied inside every Azure AI Search call, and access is denied by default. It describes where in the organisation a document belongs, which a label doesn't.

    For example, an HR document labelled Confidential for the UK should reach UK HR staff with sufficient clearance. The label supplies the clearance level. The policy adds the department and region rules. Neither one expresses the whole rule on its own.

    Status. Purview label support in RAG-OS is Roadmap, planned for the Next phase (section 9). None of the label steps described below is available today. The access policy, classification layers, SME review and default deny that the labels will feed are Available.

    6.1 How RAG-OS will use labels Roadmap

    Labels become an input to classification, not a second access engine. One access policy stays the single place where access is decided.

    1. Read the label at ingestion. Word, Excel and PowerPoint files keep label metadata either in custom document properties (MSIP_Label_…) or, in tenants that turn on co-authoring for labelled files, in the newer LabelInfo.xml format. Microsoft notes that once co-authoring is on, new label information is no longer written to the custom properties, so RAG-OS will read both. For SharePoint and OneDrive content, the Microsoft Graph extractSensitivityLabels action (v1.0, Files.Read.All) returns the label. Label IDs are resolved to a name and priority through the Graph sensitivity label API (v1.0, SensitivityLabel.Read).
    2. Map it through a customer-reviewed table. Each label maps to a RAG-OS clearance level and a confidentiality facet value. The mapping is an explicit table that the customer approves, not an automatic ranking: Microsoft says a higher label priority usually means higher sensitivity, which is not a guarantee.
    3. Record provenance, allow SME override. The tag records that it came from a Purview label, as every RAG-OS facet records its source. An SME can review and override it, and an approved review is never overwritten by a later rule.
    4. Enforce through the single access policy. The clearance level joins department, region and personal-share rules in the same filter inside Azure AI Search. A document without a clearance level is denied, so an unmapped label withholds the document rather than exposing it.
    5. Show labels in answers. Each citation shows its source's label badge, and the answer carries the highest-priority label among its sources. Microsoft 365 Copilot behaves the same way, so users see what they already expect.
    6. Optional: keep selected labels away from the model. A configurable rule can mark labels whose content is never sent to the LLM. Such documents can be cited or excluded, but not summarised.
    7. Encrypted (rights-protected) files. General-purpose parsers can't read encrypted content, but the label metadata can still be read. RAG-OS will record these files with their label and report them in the admin console. Content is decrypted only if the customer approves a Microsoft Information Protection (MIP) SDK setup. Decryption needs an identity with super-user rights over the tenant's encrypted content, so it is a governance decision for the customer.

    7Where RAG-OS stands out

    These are the areas where RAG-OS adds something the Azure building blocks don't provide out of the box. "Not found" means we found no comparable feature in the Microsoft documentation and public competitor material we reviewed on 9 October 2026. It doesn't prove that none exists.

    Configurable ABAC, denied by default

    Department, region hierarchy, clearance level and personal share, combined in one declarative policy and compiled into a filter applied inside every search. Missing attributes mean deny-all, and claim values are allow-list validated, which makes filters injection-safe. Azure's native trimming is identity-based, with OR semantics. Among the competitors we profiled, we found none that advertises an equivalent policy model.

    Works alongside native ACLs

    Azure AI Search appends its internal permission filter to any caller filter. That means source ACLs (for example SharePoint, through native ingestion) and the RAG-OS attribute policy can apply together: a document must pass both. RAG-OS covers corpora that have no trustworthy ACLs, and native ingestion covers those that do.

    Governed classification

    Layered tagging (rules, sidecars, Excel manifest, upload form, then classifiers), an SME review queue that freezes approved labels, and a recorded source for every facet. We found no comparable taxonomy, classification or review workflow in the Foundry IQ documentation. On Azure, custom enrichment also conflicts with native ACL and label ingestion within a single indexer pipeline.

    Abstain, don't guess

    RAG-OS refuses uncited answers. It abstains without calling the model when nothing permitted and relevant is found, and every refusal has a reason code. Admins can see why an answer was refused through the near-miss probe.

    Per-query token cost and stage tracing

    Token use is recorded on every answer, with one correlation ID across browser, API, queue and worker, and admins get stage-by-stage traces with replay. In Foundry IQ, token counts appear only in each response's activity log, and the MCP path drops activity and references entirely.

    Your choice of models, including Claude

    Claude on Microsoft Foundry or Azure OpenAI GPT can be the answer model. Embeddings can be self-hosted, with no per-token cost and text kept inside the deployment. Knowledge-base planning and synthesis in Foundry IQ accept Azure OpenAI models only.

    In your tenant, keyless

    RAG-OS runs in your Azure subscription with managed identity and no keys, and only entitled passages reach the model. Compared with SaaS assistants hosted outside Azure, this keeps the data path in your own tenant.

    A stable contract over fast-moving preview APIs

    Foundry IQ's governance features (permission ingestion, Purview labels, SharePoint, planning) are in Preview, and the API has changed rapidly. RAG-OS offers customers one stable product contract, and adopts the native features underneath as they mature.

    10.1 Other considerations for evaluators

    • Total cost of ownership. RAG-OS costs are Azure resources in your subscription plus LLM tokens, rather than a per-seat SaaS fee. RAG-OS reports the tokens used for every answer, so you can model cost from a pilot's real usage.
    • Security review of the access path. Ask for a threat model covering sign-in, the embed, attribute claims, filter construction and admin bypass, and review it with your security team.
    • Evaluate on your own golden questions. Build a set of questions with expected answers and citations from your own documents. Include access-leak tests: users who must not see a document should get an abstention, not an answer.
    • Side-by-side pilot. Agree a short demo script and run the same questions, users and documents through each option you are considering.
    • Data residency and model choice. Confirm the regions for search, storage and models, and which models (Claude or Azure OpenAI GPT, self-hosted or Azure OpenAI embeddings) meet your policies.
    • Preview-feature risk on the Azure side. Several native governance features are in Preview, with no SLA and changing APIs. Check their status on the linked pages before you depend on them.

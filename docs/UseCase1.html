Use Case 1: mortgage loss-mitigation document chase

How relational data, a taxonomy and an ontology combine with the RAG-OS corpus to decide whether a hardship application is complete against a specific version of a specific investor guide, and to state precisely what is missing, inside the Regulation X clock. Design for review. Phase 1, the artifacts (taxonomy, ontology, SHACL, golden cases, SQL and their checks), is built in usecase1/ and is what this page describes; no engine code has been written yet.

  • Design document · Phase 1 artifacts built
  • Synthetic investor guides
  • OWL/RDF + SHACL
  • uc1_* tables · SQLite / PostgreSQL
  • Palantir structural guidance
  • VocBench · Protégé · pySHACL
  • RAG-OS citations

Not legal advice. Regulatory points are summarised from 12 CFR 1024.41 with links to the source; interpretation must be confirmed by compliance before any of this is used on real applications.

Synthetic guidelines. "Investor A Servicing Guide v2025.1 / v2026.1" are invented for this MVP. They are shaped like real investor guides, but no requirement here is a real GSE, FHA or VA rule.

1Summary#

A homeowner falls behind and applies for help. The servicer has five business days to tell them whether the application is complete and, if not, exactly which documents are missing. Whether it is complete depends on which investor owns the loan and which version of that investor's guide was in effect.

The design separates three kinds of knowledge and lets software combine them deterministically:

  • Relational tables hold the facts of this case: who the borrower is, when the application arrived, which documents came in and how old they are.
  • The taxonomy holds the agreed words: what a "profit and loss statement" is, and that a "P&L" is the same thing.
  • The ontology holds the rules: what each guide version requires, when it applies and how recent it must be. Each rule points at the guide section it came from.

A validation engine checks the facts against the rules of the right version, and every rule that fails becomes one missing item, with the guide section and a page-level citation from RAG-OS. Language models are used only at the edges: recognising which document is which, and drafting the letter from the list. They never decide completeness.

The model follows Palantir's ontology structural guidance plus classic ontology design principles and patterns, and is checked against a catalogue of known anti-patterns (section 8).

2The business problem and the clock#

The decision. Given an application and the documents received, is the package complete against the investor guideline version that governs it, and if not, what precisely is missing?

The clock. Under 12 CFR 1024.41(b)(2)(i), when a servicer receives a loss mitigation application 45 days or more before a foreclosure sale, it must notify the borrower in writing within 5 days (excluding legal public holidays, Saturdays and Sundays). The notice acknowledges receipt and says whether the application is complete or incomplete. If it is incomplete, the notice must state the additional documents and information needed and the date by which to send them.

  • Reasonable diligence (§1024.41(b)(1)): the servicer must exercise reasonable diligence in obtaining what is needed to complete the application.
  • Evaluation (§1024.41(c)): a complete application received more than 37 days before a sale must be evaluated for all available options within 30 days.
  • Why an incorrect list is costly (§1024.41(c)(2)(iv)): once the borrower sends everything the notice listed, the application is facially complete. If the servicer later finds more is needed, it must ask promptly and treat the application as complete for foreclosure protections until the borrower has a reasonable chance to supply it. So a missing-items list that is wrong (too short or wrong items) has real consequences. The brief's phrase "an incorrect list restarts the clock" is used here as the business premise; the exact effect must be confirmed with compliance.

Sources: eCFR §1024.41 · CFPB Regulation X §1024.41 · CFPB official interpretations.

5Relational design (semantic model)#

The tables hold facts only, each stored once. They contain no rules: "self-employed borrowers need a P&L" is not a row, it is part of the ontology, so a new guide version never needs a schema change. Anything that can be computed (the governing guide version, a document's age, completeness) is derived, not stored; section 8 explains why.

The tables below are cut from usecase1/sql/uc1_create.sql when this page is built, so they always match the script. uc1_application_party, uc1_evaluation_item and uc1_evaluation_item_document are object-backed links: the last one lists the documents that satisfied an item, because one item can need several (two bank statements satisfy R5).

sql
-- Excerpt of usecase1/sql/uc1_create.sql, read when this page is built (the file is the source of truth).
-- 5 of its 11 tables; indexes and the other tables are omitted.
-- One loss-mitigation application.
CREATE TABLE uc1_application (
    application_id          TEXT NOT NULL PRIMARY KEY,
    loan_id                 TEXT NOT NULL REFERENCES uc1_loan (loan_id),
    received_at             TIMESTAMP NOT NULL,
    foreclosure_sale_date   DATE,
    hardship_reason         TEXT NOT NULL           -- taxonomy id (uc1_hardship_reason): a fact of this application
        CHECK (length(hardship_reason) > 0)
    -- deliberately absent: resolved guide version, completeness status (both derived; see header)
);

-- Object-backed link: Application x Borrower. Role and circumstances as of this application.
-- Exactly one 'primary' per application: at most one is enforced by ux_uc1_application_party_primary below;
-- at least one is an invariant tested by check_sql.py (a row-level constraint cannot see other rows).
CREATE TABLE uc1_application_party (
    application_party_id    TEXT NOT NULL PRIMARY KEY,
    application_id          TEXT NOT NULL REFERENCES uc1_application (application_id),
    borrower_id             TEXT NOT NULL REFERENCES uc1_borrower (borrower_id),
    role                    TEXT NOT NULL CHECK (role IN ('primary', 'co_borrower')),
    employment_type         TEXT NOT NULL           -- taxonomy id (uc1_employment_type), as of this application
        CHECK (length(employment_type) > 0),
    has_rental_income       BOOLEAN NOT NULL CHECK (has_rental_income IN (TRUE, FALSE)),
    UNIQUE (application_id, borrower_id)
);

-- A document received for an application (an Evidence in the ontology).
-- Structs, as prefixed column groups (the bridge maps each group to one struct):
--   period_*          -> Period         (start + end; a start needs an end, end >= start)
--   signature_*       -> Signature      (signed + date; NULL signed = not applicable; a date only when signed)
--   classification_*  -> Classification (doc type + confidence + method + reviewer; method always known;
--                                        'human' needs a reviewer, a machine method needs a confidence)
CREATE TABLE uc1_submitted_document (
    submitted_document_id       TEXT NOT NULL PRIMARY KEY,
    application_id              TEXT NOT NULL REFERENCES uc1_application (application_id),
    received_at                 TIMESTAMP NOT NULL,
    document_date               DATE,
    -- struct: period
    period_start_date           DATE,
    period_end_date             DATE,
    -- struct: signature
    signature_signed            BOOLEAN CHECK (signature_signed IN (TRUE, FALSE)),
    signature_date              DATE,
    -- struct: classification (taxonomy id + how it was decided)
    classification_doc_type     TEXT NOT NULL       -- taxonomy id (uc1_doc_type)
        CHECK (length(classification_doc_type) > 0),
    classification_confidence   DOUBLE PRECISION CHECK (classification_confidence BETWEEN 0 AND 1),
    classification_method       TEXT NOT NULL CHECK (classification_method IN ('classifier', 'llm', 'human')),
    classification_reviewed_by  TEXT,
    rag_doc_id                  TEXT,               -- the uploaded file in RAG-OS
    CHECK (period_start_date IS NULL OR period_end_date IS NOT NULL),
    CHECK (period_end_date IS NULL OR period_start_date IS NULL OR period_end_date >= period_start_date),
    CHECK (signature_date IS NULL OR signature_signed = TRUE),
    CHECK (classification_method <> 'human' OR classification_reviewed_by IS NOT NULL),
    CHECK (classification_method = 'human' OR classification_confidence IS NOT NULL)
);

-- Object-backed link: Evaluation x Requirement. One outcome per requirement per evaluation.
CREATE TABLE uc1_evaluation_item (
    evaluation_item_id          TEXT NOT NULL PRIMARY KEY,
    evaluation_id               TEXT NOT NULL REFERENCES uc1_evaluation (evaluation_id),
    requirement_id              TEXT NOT NULL,      -- requirement id within the evaluation's guide version, e.g. 'R4'
    outcome                     TEXT NOT NULL CHECK (outcome IN ('met', 'missing', 'not_applicable')),
    reason                      TEXT,               -- engine explanation; must not contain PII (no names, ids)
    UNIQUE (evaluation_id, requirement_id)
);

-- Which documents satisfied an item. Many-to-many: 'two most recent bank statements' is met by two documents.
CREATE TABLE uc1_evaluation_item_document (
    evaluation_item_id          TEXT NOT NULL REFERENCES uc1_evaluation_item (evaluation_item_id),
    submitted_document_id       TEXT NOT NULL REFERENCES uc1_submitted_document (submitted_document_id),
    PRIMARY KEY (evaluation_item_id, submitted_document_id)
);

Where: the uc1_* tables live in their own SQLite file, .data/uc1.db (git-ignored), never in the product state database; the same scripts are proven on PostgreSQL 16 in a dedicated uc1 schema. They are created by usecase1/sql/uc1_create.sql (which expects an empty schema), seeded by uc1_seed.sql and removed by uc1_drop.sql. These are not Alembic migrations, so the product schema is never touched.

Version resolution: the governing guide version is derived, never stored: the loan investor's version in effect on the application's received date. The query below shows the rule; it is illustrative and not part of the script. The version is recorded only on uc1_evaluation, which freezes it together with the outcome. If an investor's own policy says otherwise, that becomes a column, not code.

sql
-- Illustrative only: this query is NOT in uc1_create.sql. The governing guide version is derived, never stored:
-- the loan investor's version whose effective dates contain the application's received date
-- (effective_to_date NULL = open-ended). PostgreSQL syntax; in SQLite write date(a.received_at).
SELECT gv.guideline_version_id
  FROM uc1_application a
  JOIN uc1_loan l               ON l.loan_id = a.loan_id
  JOIN uc1_guideline_version gv ON gv.investor_id = l.investor_id
 WHERE a.application_id = :application_id
   AND gv.effective_from_date <= CAST(a.received_at AS DATE)
   AND (gv.effective_to_date IS NULL OR gv.effective_to_date >= CAST(a.received_at AS DATE));

Naming: singular table names; dates end _date and timestamps _at; qualified names (outcome, classification_confidence) instead of a generic status or value. Simplification: uc1_loan.investor_id is a direct link; see 8.2.

6Taxonomy: what, how, where#

  • What: four controlled vocabularies.
    • uc1_doc_type is hierarchical, with synonyms: Application › MAA, Income › Paystub · P&L · Benefit letter, Assets › Bank statement, Hardship › Hardship statement, Tax › 4506-C, Property › Lease.
    • uc1_employment_type, uc1_hardship_reason and uc1_workout_option.
    • Real words, synthetic rules: labels and synonyms use real industry document names (Form 710, 4506-C, RMA) so the classifier can recognise real documents; only the requirements (section 7) are synthetic.
    • Group concepts are not classification targets. Application, Income, Assets, Hardship, Tax and Property only group the hierarchy: the converter keeps them out of the classifier, and a document matched only to a parent means needs-review, never a valid type.
  • Edited in: VocBench 3 (section 9.2), by the SMEs, with a validator approving each change. VocBench holds the vocabulary as SKOS; its Turtle export is the single source of truth. It was bootstrapped once from the seed usecase1/taxonomy/uc1-taxonomy.seed.skos.ttl.
  • How RAG-OS uses it: a converter (Phase 2) generates the YAML below from the export, in exactly the shape RAG-OS already uses for facets (FacetDef: id, label, parent, synonyms, description, classify). The mapping is fixed: a concept's skos:notation (= its IRI local name) is the value id, skos:prefLabel the label, skos:altLabel the synonyms, skos:broader the parent, and skos:definition the value's description; each scheme's IRI local name is the facet name and its skos:prefLabel the facet label. The existing embedding classifier can then label incoming borrower documents, and low-confidence labels go to the existing review queue, with no new mechanism.
  • Where: the SKOS export usecase1/taxonomy/uc1-taxonomy.skos.ttl in git, imported by the ontology (skos:broader, skos:altLabel), so rules and classifier use the same concepts. The generated usecase1/taxonomy/taxonomy.yaml stays out of the product facets.yaml until the use case is adopted.
  • Who: loss-mitigation operations SMEs, the same ownership model as RAG-OS facets.

7Ontology: construction#

Approach: competency questions first. The ontology is only as big as the questions it must answer:

  1. Which guide version governs application A?
  2. Under that version, which requirements apply to A's borrower?
  3. Which of those are not satisfied by a submitted document of the right type, signed and recent enough?
  4. For each unmet requirement, which guide section says so, and where is it in the source text?

# usecase1/ontology/uc1-requirements.shapes.ttl: the whole file, read when this page is built.
# =====================================================================================================================
# Use Case 1: the completeness template (SHACL-SPARQL). Written once by an engineer; SMEs never edit it.
#
# One shape checks EVERY document requirement of the governing guide version. Requirements are data (one file per
# guide version, investor-a-<version>.ttl); this template only reads their parameters:
#   uc1:documentType                      the taxonomy concept that satisfies it (narrower concepts count too)
#   uc1:condition  onProperty/expectedValue  when it applies (tested on the application or any of its parties)
#   uc1:recency    maxAgeDays             each satisfying document is at most this old at receipt
#                  signatureRequired      each satisfying document is signed
#                  minCount               at least this many satisfying documents (default 1)
#                  mostRecentMonths       a window of N whole months before the month of receipt (1 = the month
#                                         before) in which periods must end; with minCount, that many DISTINCT
#                                         months must be covered. A period ending in the month of receipt does not count.
# Each violation is one missing item; its message is the requirement's own label (which cites its guide section).
#
# Inputs the bridge must provide per application: uc1:governingVersion, uc1:ageAtReceiptDays and
# uc1:monthsBeforeReceipt (all derived, never stored). Data shape problems are reported separately by
# uc1-dataquality.shapes.ttl, so a data defect is never presented to a borrower as a missing document.
# SYNTHETIC MVP. Verified by usecase1/checks/run_golden.py.
# =====================================================================================================================

@prefix uc1:      <https://rag-os.example/uc1#> .
@prefix uc1shape: <https://rag-os.example/uc1/shapes#> .
@prefix owl:      <http://www.w3.org/2002/07/owl#> .
@prefix rdfs:     <http://www.w3.org/2000/01/rdf-schema#> .
@prefix sh:       <http://www.w3.org/ns/shacl#> .
@prefix skos:     <http://www.w3.org/2004/02/skos/core#> .
@prefix xsd:      <http://www.w3.org/2001/XMLSchema#> .

<https://rag-os.example/uc1/shapes>
    a owl:Ontology ;
    rdfs:label "Use Case 1 completeness template (SHACL)"@en ;
    sh:declare
        [ sh:prefix "uc1" ;  sh:namespace "https://rag-os.example/uc1#"^^xsd:anyURI ] ,
        [ sh:prefix "rdfs" ; sh:namespace "http://www.w3.org/2000/01/rdf-schema#"^^xsd:anyURI ] ,
        [ sh:prefix "skos" ; sh:namespace "http://www.w3.org/2004/02/skos/core#"^^xsd:anyURI ] .

    a sh:NodeShape ;
    rdfs:label "Every applicable requirement of the governing guide version is satisfied"@en ;
    sh:targetClass uc1:Application ;
    sh:sparql [
        a sh:SPARQLConstraint ;
        sh:prefixes <https://rag-os.example/uc1/shapes> ;
        sh:message "{?label}" ;
        sh:select """
            SELECT $this ?req ?label
            WHERE {
                $this uc1:governingVersion ?gv .
                ?req uc1:guidelineVersion ?gv ;
                     uc1:documentType ?type ;
                     rdfs:label ?label .

                # Applies only if every condition holds on the application or on one of its parties.
                FILTER NOT EXISTS {
                    ?req uc1:condition ?c .
                    ?c uc1:onProperty ?p ;
                       uc1:expectedValue ?v .
                    FILTER NOT EXISTS { { $this ?p ?v } UNION { $this uc1:parties ?pt . ?pt ?p ?v } }
                }

                OPTIONAL { ?req uc1:recency/uc1:signatureRequired ?sig }
                OPTIONAL { ?req uc1:recency/uc1:minCount ?minCount }
                OPTIONAL { ?req uc1:recency/uc1:mostRecentMonths ?months }

                # Each satisfying document contributes one key: itself, or its month when months are counted.
                OPTIONAL {
                    $this uc1:documents ?d .
                    ?d uc1:classification/uc1:docType/skos:broader* ?type .
                    OPTIONAL { ?d uc1:ageAtReceiptDays ?age }
                    OPTIONAL { ?d uc1:monthsBeforeReceipt ?m }

                    FILTER (!BOUND(?sig) || !?sig || EXISTS { ?d uc1:signature/uc1:signed true })
                    FILTER (!BOUND(?months) || (BOUND(?m) && ?m >= 1 && ?m <= ?months))
                    BIND (IF(BOUND(?months), STR(?m), STR(?d)) AS ?key)
                }
            }
            GROUP BY $this ?req ?label
            HAVING (COUNT(DISTINCT ?key) < MAX(COALESCE(?minCount, 1)))
            """ ;
    ] .

Why SHACL: it is the W3C standard for "does this graph satisfy these constraints?". Its validation report lists every violation with its message, which is the missing-items list. The message is the requirement's own label, and the requirement cites its section, so every item is traceable. Why rules as data: "90 days" is written once, in the requirement, and the template is the same for every version. So v2025.1 and v2026.1 differ only in their data files (investor-a-2025.1.ttl, investor-a-2026.1.ttl). A new version is a new file, and old ones stay for audit and for re-checking older applications. Date arithmetic is derived by the bridge (ageAtReceiptDays, monthsBeforeReceipt), both because SPARQL date subtraction is not portable and because a derived value must not be stored (8.2). Dates are written as xsd:dateTime at midnight ("2026-01-01T00:00:00"^^xsd:dateTime), because OWL 2 has no date-only datatype and HermiT (also inside Protégé) rejects one; the SQL tables keep real DATE columns and the bridge writes them at midnight. The principles behind these choices are in section 8.

Normalization and derived properties
"Store each fact once. Use derived properties for convenience." 8.6 Design-review checklist

Run this before every new guide version, new document kind or model change. Every answer must be yes.

  1. Is each new fact stored exactly once, and is everything computable derived rather than stored?
  2. If a value is deliberately denormalized (like the evaluation snapshot), is the reason written down?
  3. Are related fields grouped into a struct rather than loose properties?
  4. Is a new document kind only a new taxonomy concept (its documents are SubmittedDocuments, so «Evidence»), with no new class or rule?
  5. Does every new link answer a domain question, and does a link with its own facts have its own object?
  6. Are names singular, concrete, qualified and readable from both ends? Do dates and timestamps follow the suffix rule?
  7. Is a new guide version only a new data file, with no new class and no code change?
  8. Does every requirement cite its guide section, and does that section exist in the ingested guide?
  9. Is every new term in the VocBench taxonomy (not invented in the ontology), with its synonyms as labels?
  10. Is there still one type per entity, with row- and column-level rules instead of copies?
  11. Do the golden cases still pass, with no loss of precision?

9.4 pySHACL: running SHACL

Purpose. Decide, for one application, which requirements of the governing guide version are not met.

How a SHACL check works.

  1. Data graph: the bridge merges the ontology core, the SKOS taxonomy, the governing version's requirements file and the application's facts from the uc1_* tables, including derived values such as ageAtReceiptDays.
  2. Targets: each shape picks its focus nodes. Ours targets every uc1:Application.
  3. Constraints: the shape's SPARQL template returns one row per requirement that applies and is not satisfied.
  4. Report: a W3C validation report with sh:conforms and one sh:ValidationResult per row, giving the focus node, the source shape and the message (the requirement's own wording, with its section).

SHACL is written once, by an engineer: the single template in section 7, plus the separate data-quality shapes (uc1-dataquality.shapes.ttl), which check the data itself and are never reported as missing documents. Subject-matter experts never edit SHACL; they change requirement data in Protégé. pySHACL supports these SPARQL-based constraints by default. Its -a/advanced switch enables SHACL Advanced Features (rules, custom targets), which this design does not use.

11Multi-agent? Recommendation#

Recommendation: an orchestrated workflow with a deterministic core, not autonomous agents.

StepWho does itWhy
Recognise documents (type, dates, signed)Classifier / LLM extraction, confidence-gatedMessy input is where models help; below the threshold a person confirms (the existing review queue).

Calling these "agents" is fine, but give each one a narrow contract (typed input, typed output) and keep the decision out of any model's hands. This mirrors how RAG-OS already treats answers: retrieval is filtered deterministically, the model only writes from what it is given, and a grounding guard checks the result.

14.2 Artifacts first, code second

Yes, and it is the recommended order; Phase 1 has done exactly this.
